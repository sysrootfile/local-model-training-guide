This is our sixth **runnable example project** and [Example 5](/en/ornekler/yerel-rag/)'s natural continuation: the same zero-pip pipeline (retrieval with bge-m3, generation with qwen2.5:3b), but this time two abilities indispensable in the real world are added — **we don't write the data by hand, we download it from Turkish Wikipedia at runtime**, and **we split the long articles into overlapping pieces**. The subject: Istanbul public transit. No GPU at all; an internet connection and Ollama suffice.

:::note[Ran on this machine]

## 1) What are we doing?

**The goal:** a local question-answering assistant "knowing Istanbul public transit". The knowledge source is Wikipedia's 8 articles on Istanbul transit — the public transit overview, the metro, Marmaray, the Tünel, the T1 tram, the metrobus, İETT and the sea buses.

The pipeline contains **two new steps** (the bold ones) relative to Example 5's diagram:

```text
the tr.wikipedia.org API (8 articles) ──► text cleaning ──► chunking (~800 characters + overlap)
        │
        ▼
125 pieces ──► vectorizing with bge-m3 (/api/embeddings) ──► the index (in memory)
        │   when a question arrives:
        ▼
the question vector × the piece vectors ──► cosine similarity ──► the best 4 pieces
        │
        ▼
context + question ──► qwen2.5:3b (/api/chat) ──► the answer + an [Article#piece] source
```

In Example 5 every document was hand-written and a single piece; that was a deliberate simplification. In real projects the corpus **comes from outside** (the internet, files, a database) and is **long** — the two jobs those two facts create, data loading and chunking, are this page's real subject.

## 2) The setup

No pip needed; the internet, Ollama and two models:

```bash
ollama pull bge-m3                        # the embedding model (~1.2 GB)
ollama pull qwen2.5:3b-instruct-q4_K_M    # answer generation (~1.9 GB)

python viki_rag.py                              # the whole demo: the corpus + 2 questions + two tests
python viki_rag.py --soru "Marmaray kaç kilometre?"   # ask a single question
python viki_rag.py --test                       # only the retrieval test

python olc.py                                   # measures the threshold bands (2 models, ~17 min)
python hibrit.py                                # the vector / BM25 / RRF race (~10 min)
```

The two measurement scripts in the same folder import `viki_rag.py` — i.e. the corpus and the questions come from a single source; the logs are written under `cikti/`. All the numbers used on this page came from those logs.

:::note[Half the index time wasn't the model's work — now this isn't a guess, it's a re-measurement]
This script, firing one HTTP request per piece, used `http://localhost:11434` on 2026-10-15. The measurement on the [Speed and Cost](/en/kullanim/hiz-ve-maliyet/) page had found that on Windows the `localhost` name resolves in **~2.03 s** per request, dropping to **0.00 s** with `127.0.0.1`; the "501.8 − 125×2.03 ≈ 248 s" split was, at that moment, only arithmetic — i.e. an estimate derived from two measured components. On 2026-10-16 the address was switched and the same script re-run on the same machine, and the prediction held: **501.8 → 246.6 s**, the measured drop **255.2 s**, the predicted share **253.8 s**. `olc.py` and `hibrit.py` also fell in the same direction (495.7 → 259.2 and 529.3 → 253.0 s) and in all three the **retrieval results stayed line-by-line identical**: name resolution doesn't affect the ranking, it only eats the clock.
:::

**The instructive MISS: overview-article pieces are magnets.** On the question "What route does the Metrobüs follow?", 1st place wasn't taken by the Metrobüs article but by a piece of the *Public transit in Istanbul* overview article. Since overview texts touch many subjects, they produce mid-level similarity to many questions; on specific questions the piece "knowing a little of everything" can get ahead. `olc.py` saw these escapes in the paraphrase set too: on both the "Where does the Metrobüs line go from and to?" and "Which is the oldest line in the Istanbul metro?" questions, the overview article stole first place. The fix is visible in hit@4: growing k brings the right article into the context — but **k is the number of pieces added to the context**; growing it raises the hit while also polluting the context and stretching the CPU time. Managing that trade-off by measuring: [RAG Evaluation](/en/rag/rag-degerlendirme/).

**The inherited threshold collapsed in the measurement — and the page confesses it.** `WEAK_THRESHOLD = 0.35` hadn't been measured for this corpus; it was carried over from Example 5. The 2026-10-15 run's log showed the 0.344 out-of-scope question only barely passing that threshold: the margin **0.006**. Then this margin was genuinely measured (`olc.py`, 8 out-of-scope questions): the band **0.321 - 0.485**. So 0.35 was passing *through* the out-of-scope questions — except the pizza question, 6 of the 7 wouldn't have triggered the warning. The measured threshold suggestion is **0.541** (the bands' middle); the constant in the code was raised to **0.54** on 2026-10-15 and the separation margin recorded as **+0.113**. The out-of-scope record above, with this form of the threshold, gives the same warning with a ~0.20 margin. In the 2026-10-16 re-run the bands, hits and citations came out exactly the same: the threshold behavior wasn't affected by the address change.

Note: all those passing the threshold are irrelevant questions containing the word "Istanbul" (a cheap hotel 0.454, the stock exchange 0.473, Galatasaray 0.469). The out-of-scope test set should be built not from obvious irrelevancies like pizza recipes but from questions **resembling the corpus's topic**; otherwise the threshold doesn't catch real life's semi-meaningful queries.

**The citation came out honest this time — which isn't proof of stability.** In Example 5's out-of-scope test the model had attached a **fabricated source** to the correct "there isn't" answer; here, while saying "no information", it showed the pieces genuinely retrieved (`İETT#13`, `Marmaray#9`...). The same model, two different behaviors: small models' citation discipline varies from question to question. That's why you trust the citation not with the model's word but with **your retrieval record** — checking the shown ids against the retrieved ids is a one-line programmatic check.

## 6) Four subtleties to note in the code

### a) The Wikipedia API's two rules

- **A User-Agent is mandatory:** Wikimedia blocks meaningless clients; the script connects with a `User-Agent` header introducing itself (`VIKI_UA`). This is what should be done in every script using a web API, and what most examples skip.
- **One article per request:** full-text extraction (`explaintext`) is limited to `exlimit=1` in the API; the script pulls the 8 articles one by one. `redirects=1` carries the redirects to the right title; a missing article arrives with the `missing` flag — instead of crashing, the script prints a WARNING and skips.

The titles aren't assumed in advance: the 8 articles on this page were queried and verified one by one on 2026-10-15; when building your own list too, try each title once.

### b) Chunking: paragraph-based, ~800 characters, overlapping

`parcalara_bol()` contains three decisions:

1. **Cut at the paragraph boundary:** blind cutting by characters splits the sentence in the middle; in Turkish, with its suffixing structure, that's the most expensive way of splitting meaning. The script takes paragraphs longer than 40 characters and stacks them up to the target (article headings `== ... ==` are dropped).
2. **A target of ~800 characters:** a small piece → meaning alone; a big piece → retrieval blurs and the context swells. 800 is a balanced point for this corpus — in your corpus choose by measuring across the 400-1200 range (the experiment suggestion below).
3. **Overlap:** when a chunk fills, the **last paragraph** is carried into the new chunk. A fact split at a paragraph boundary is thus found on both sides; if the residue is shorter than 200 characters it's merged into the last chunk (a single-sentence piece is noise in the index).

### c) k = 4: the measurement should reflect k

As the corpus grew from 8 documents to 125 pieces, the number of pieces added to the context was raised from 2 to 4, and the test reports it: hit@**4**. 4 × 800 ≈ 3,200 characters, in Turkish roughly 1,000-1,600 tokens — it fits Ollama's default 4,096 context window. If a bigger k or bigger pieces overflow the window, `num_ctx` is raised under `options`; otherwise the context is silently truncated.

### d) The license: CC BY-SA's price is attribution

Wikipedia texts are CC BY-SA licensed: reusing the text is free, but **attributing the source is mandatory**. The script prints a license reminder at the end of every run. We don't embed the corpus into the repo — pulling it from the API at every run both reduces the license burden and points to the article's current state.

## 7) Try it with your own corpus

1. Replace the `WIKI_TITLES` list with your domain's articles — verify each title once in Wikipedia search.
2. Write your own question-expected-article pairs into `TEST_QUESTIONS`; measure hit@1/hit@4 with `python viki_rag.py --test`.
3. Play `TARGET_PIECE` across the 400-1200 range and watch how the hit changes — the chunk size is the cheapest lever for improving retrieval quality.
4. Re-measure the threshold on your own corpus: the band method and the hit@k/MRR detail in [RAG Evaluation](/en/rag/rag-degerlendirme/); the smaller sibling script in [Example 5](/en/ornekler/yerel-rag/). The effect of changing the chunk size (`TARGET_PIECE`) and the search method: [Chunking and Hybrid Search](/en/rag/parcalama-ve-hibrit-arama/).

:::tip[What changed from Example 5 to Example 6 — and what didn't]
`embed()`, `cosine()`, `retrieve()`, `answer()` are nearly verbatim the same; only two abilities changed: **data loading** and **chunking**. The RAG skeleton is learned once; the difference between real projects consists of the questions "where's the data from?" and "how shall we chunk?". Both's effect on quality is seen only through measurement.
:::
